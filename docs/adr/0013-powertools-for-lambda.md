# 0013. Powertools for AWS Lambda (.NET): adopt Idempotency behind our own interface; build the redaction; decide Metrics and Tracing in the first Lambda spike

**Status:** Proposed; the owner confirms · **Date:** 2026-11-05 · **Decided by:** proposed from the evaluation roadmap task 2.1 asks for; not yet confirmed by the owner

## Context

The [logging standard](../06-logging-observability.md#on-lambda) says to evaluate **Powertools for AWS Lambda (.NET)** before the kit writes its own logging, metrics, tracing and idempotency, because "buy-or-adopt beats build when a maintained library already does the job". The platform has two real duplications that the kit would remove ([strategy](../00-strategy.md)): **PII redaction written twice** (Hyvva and the-hive each have a pattern list of about 39 lines) and **webhook idempotency written twice** (the-hive's billing and booking-site services each have a DynamoDB repository of about 64 lines). The first application, `mortgage-analytics`, already logs through `ILogger` with `[LoggerMessage]`, a request id in a scope and one summary line per request.

What was read on 2026-11-05 (the documentation pages, the NuGet metadata and the repository; nothing was installed or run):

- **What it is.** An AWS-owned toolkit for Lambda, with NuGet packages `AWS.Lambda.Powertools.Logging`, `.Metrics` (and `.Metrics.AspNetCore`), `.Tracing`, `.Idempotency`, `.Parameters` and `.BatchProcessing`. Current release **3.2.2 (2026-05-25)**; the repository is active (not archived, last push 2026-11-04) with 180 stars. The packages target `net8.0` and `net10.0` (their NuGet metadata), and Lambda has had a managed `dotnet10` runtime since 8 January 2026. The package metadata says Apache-2.0 while the repository's `LICENSE` file is the MIT-0 text; both are permissive, and the first adoption should confirm which applies.
- **Its stated limits.** Its tenets begin "**AWS Lambda only**": utilities "might work with web frameworks and non-Lambda environments, though they are not officially supported". Our applications are Minimal APIs that must also run under Kestrel on a laptop, in tests and in Docker ([ADR 0006](0006-lambda-granularity.md)).
- **Logging.** JSON to standard output, enriched with Lambda context and cold start, sampling, `ILogger` and `ILoggerFactory` support, message templates, a custom formatter, native AOT. The page has **no redaction or masking feature**; the nearest sentence is that logging the incoming event is off by default "to prevent sensitive info being logged".
- **Metrics.** CloudWatch Embedded Metric Format written to standard output; up to 100 metrics per blob, at most 30 dimensions; a cold start metric; AOT from 1.7.0; an ASP.NET Core middleware and endpoint filter. Its documented API is its own (`Metrics.AddMetric`); the page mentions no `System.Diagnostics.Metrics` integration.
- **Tracing.** "An opinionated thin wrapper" over the **AWS X-Ray .NET SDK** (it says it uses X-Ray rather than OpenTelemetry "for optimal cold start"); attributes and subsegments; AOT from 1.5.0, but instrumenting SDK clients with `Tracing.RegisterForAllServices()` "is not supported on AOT mode".
- **Idempotency.** Stores a hash of the event (or a JMESPath-chosen part of it) and the **JSON-serialized result** in **DynamoDB, the only supported store**; marks a record in progress so a concurrent duplicate is refused; expires records (one hour by default); recovers when an invocation times out; optional payload validation and a per-instance cache; responses must be under 400 KB; about two DynamoDB requests per invocation; `[Idempotent]` is an attribute woven in by `AspectInjector`; AOT from 1.3.0.

## Decision

We will **adopt Powertools Idempotency**, used through a small interface of our own (the kit's `IIdempotencyGuard` or similar) with the Powertools adapter in the Infrastructure layer, so the Application layer never references an AWS package. We will **build the redaction ourselves**, lifted from the two existing pattern lists, as a component that works at the `ILogger` level and so sits equally on our own JSON console output or on Powertools Logging. We will **not build metrics or tracing kit code now**: the choice between Powertools Metrics and Tracing and an OpenTelemetry-based setup is made by the first Lambda deployment's spike, measuring cold start and AOT behaviour ([ADR 0006](0006-lambda-granularity.md), [document 6, open decisions](../06-logging-observability.md#open-decisions)).

## Alternatives considered

| Option                                                | Good                                                                                                        | Costs                                                                                                                                                                                               | Why not (or why)                                                                                                                   |
| ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Adopt all four utilities                              | Least code; one vendor-maintained set; consistent Lambda fields in logs, metrics and traces                 | Lambda-only by its own tenets; logging has no redaction; a static metrics API of its own (no `System.Diagnostics.Metrics` bridge is documented); X-Ray SDK not OpenTelemetry; AOT limits in tracing | Our code must also run outside Lambda, and redaction is our main logging need; metrics and tracing choices are open until measured |
| Build all four ourselves                              | Fits our standards exactly; no AWS package in the kit                                                       | Idempotency is hard to get right (locking, expiry, timeouts, concurrent duplicates); metrics (EMF) and tracing are well-solved problems                                                             | The two existing idempotency copies are the evidence that building it per app is the costly path; a maintained one exists          |
| Adopt Idempotency; build redaction; defer the rest    | Takes the part that is hard and already solved; builds the part nobody sells us; waits for data on the rest | Two ways of doing observability for a while; the spike must be done before the first Lambda deploy                                                                                                  | **Chosen**                                                                                                                         |
| Adopt Logging, Metrics and Tracing; build idempotency | Gets the Lambda-aware fields for free                                                                       | Keeps the duplicated idempotency code that is the strongest case for a library                                                                                                                      | Backwards: the strongest reason to adopt is the one it skips                                                                       |

## Consequences

- **Easier:** webhook and command idempotency stops being written per application. The two 64-line DynamoDB repositories become one adapter, and the replay tests (testing strategy, item 12) are written once against the interface.
- **Harder:** idempotency needs a DynamoDB table with a TTL attribute and the four DynamoDB permissions, in the capability's construct and asserted by a CDK test. The stored response is **personal data at rest for its lifetime** (one hour by default), so the table is encrypted, its expiry is explicit, and the `[Idempotent]` method returns only what may be stored. The the-hive repositories only _record an event id and ignore a repeat_; Powertools _returns the stored result of the first call_. For a webhook these can differ, and the first use decides which behaviour the guard promises.
- **Dependencies.** `AWS.Lambda.Powertools.Idempotency` brings `AWSSDK.DynamoDBv2` 4.x, `Amazon.Lambda.Core` and `AspectInjector`; each new package needs its [primer](../10-documentation-standard.md#primers) in the change that adds it.
- **Not yet known** (the spike answers these): the cold-start cost of each utility in a Minimal API on the `dotnet10` runtime, native AOT behaviour of the whole set, and whether Powertools Logging can be used as a formatter beneath our redaction. None of this was run.
- **To do:** the redaction and logging library is board task 21 of this repository's [work board](../work-board.md); it follows this decision and does not wait for Powertools. When the first application is deployed to Lambda, run the spike and write the follow-up ADR for Metrics and Tracing.
- **Revisit when:** the spike shows Powertools Logging is cheap and compatible (then adopt it under the redaction), Powertools adds a second idempotency store or built-in masking, the project changes owner or becomes unmaintained (no release for a year), or a requirement needs idempotency outside Lambda.
